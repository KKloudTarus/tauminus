# ADR 0030: End-to-end encrypted sync

- Status: accepted
- Date: 2026-10-24

## Context

v0.5 syncs saved hosts between a user's devices without an account: to a
git remote, S3-compatible storage, or a folder a sync tool already
copies. Its exit criteria: two devices edit the same host offline, then
sync without data loss; the target holds only ciphertext. The roadmap
named `age` for encryption and a CRDT library (`automerge` or `yrs`) for
conflicts.

A panel of three weighed it on frozen criteria: merge correctness 30%,
security 25%, complexity and dependency cost 20%, performance at 10 000
hosts 15%, backend fit 10%. One advocate built `automerge` 0.12 into a
benchmark; one argued for a merge of Tauminus's own records; an
architecture review placed the pieces.

What the panel found:

- `automerge` merged two devices' 100 offline edits each into a 10 000
  host document in 16 ms, from a 215 KB snapshot. Used as it comes, it
  lost an edit made to a host another device deleted (a deleted key wins),
  and let two group moves make a cycle: both need handling outside the
  library. Its history keeps every value ever written, so a credential
  synced once stays in the ciphertext after it is taken off. It brings 52
  crates, two of them prereleases, and had five breaking releases in six
  months.
- Last-writer-wins per field, stamped with a hybrid logical clock, is a
  state-based CRDT: merging is commutative, associative and idempotent.
  Hosts are keyed records with stable random ids and a dozen fields, and
  `Inventory::new` already checks every invariant a merge can break.
- `age` does not authenticate the sender: whoever holds the recipient's
  public key can write a snapshot others accept.

## Decision

### Records stamped per field, merged as a CRDT

Each synced record (a host, a group, a snippet) is a map of fields, each
with a stamp: wall-clock milliseconds, a counter, and the device's id,
compared in that order. Merging keeps, per field, the value with the
highest stamp. A delete wins over any edit: a deleted record keeps a
tombstone, its stamp and no values, and record ids are random, so none is
reused. An edit the delete beat is a clash the editing device sees.
Keyed lists merge per element: `tags` as a set, `env` by name, forwarding rules by id. Ordered
lists (`jumps`, `startup`) are one field each. The roadmap's "with a
CRDT" holds; the library does not come along.

Stamps live in a local base, `sync-state.json` beside `hosts.json`: the
merged state as of the last sync. A sync diffs the saved lists against
it, so every changed field gets a new stamp; nothing else in the app
changes how it saves. An edit is stamped when it is synced, not when it
is made: of two devices that set one field offline, the one that syncs
later wins. Each sync lists what it settled against the other devices:
a field both set, and a record deleted on one and edited on the other.
The object it writes carries that list, so the device whose value lost
is told on its next sync as well.

A merge is written beside the base (`.staged`) before the lists are
saved; the base takes hosts and snippets as soon as each list is saved,
and the publish comes last. A sync that stops anywhere (the target went
away, the app closed) reads a value its lists took from a merge as that
merge's, keeps the clashes it has not told, and the next sync publishes.
A device's next object number is one past its last, or past the one a
cut-short sync wrote; a number further on is the target's and is removed.
A device with no base (new, or reinstalled with old lists) takes the
target's values for records the target holds, lists its own that lost,
and deletes nothing, until a sync of its is saved whole.

A tombstone takes about 45 bytes and is dropped 90 days after the
delete. Every device writes its object at least every 30 days, and an
object not written for 90 days is a device gone: it is not read, so what
it holds cannot bring a deleted record back. A device offline longer than
that, still holding the record, may, and so may one whose clock ran fast
by the time it ran fast. What a deleted record held leaves the target as
each device writes its next object. Stamps more than an
hour ahead of a device's clock are merged, but do not move its clock, and
the user is told.

### Repaired in the domain, refused at the limits

Two valid states can merge into an invalid one. `Inventory::repaired`,
in the domain, is deterministic, so every device repairs alike: a cycle
loses the parent of its lowest group id, a host whose group is gone moves
to the root. A host's tags, variables and forwarding rules that two
devices grew past a host's limits keep the first by key or place, and the
user is told. More hosts or groups than the limits allow stops the sync
instead of dropping any.

### One writer per object, sealed with the vault's primitives

The target holds a key file and one directory per device, named by a
random id. A device writes only its own objects: its whole merged state,
one new object for an edit of its own at once, and for a base only the
others changed an hour later, so edits elsewhere cost each device at most
one object an hour, and the fleet at most one per device an hour; its older ones are then removed, so no object keeps for long what
was deleted or replaced since. A sync with
nothing new on either side compares a hash of the lists and the object
numbers against a small state file, and reads neither the base nor any
object. An object that fails its checks (a bad seal, a file too large, a link
or a folder) waits an hour before it is tried again, doubling to 32 hours
and told the first time only, by its exact
number, so a forged one far ahead hides nothing, and one a sync tool was
still copying reads whole later. At most three fail per device; devices
read before come first, and devices new to this one share sixteen
failures a sync, so ids a target invents crowd out none. One the target
failed to send is tried on the next sync. A device's next number skips
any a forged object held. This device's own objects past the number
its state holds (a sync cut short, a state restored from a backup) count
if they open under the key; any other is removed before the next is
written. A doc spells each device id once,
in a table, and a stamp as `[ms, n, device]`; the object is deflated
before it is sealed. At 10 000 hosts an object is about 1 MB. Git never merges,
S3 needs no conditional writes, and a sync tool never makes a conflict
copy. Each object is sealed with XChaCha20-Poly1305 under a key HKDF
derives from a random 256-bit sync key, so only a device holding the key
writes one others accept. The key file holds the sync key wrapped by a
passphrase through Argon2id, as the vault wraps its key, at no less than
19 MiB and 2 passes, from a passphrase of at least 12 characters: anyone
with the target can try passphrases against it. A new device joins with
the target's location and the passphrase, and keeps the sync key in its
vault. These are the vault's primitives; no crate is added,
and `age` is not used.

Each object carries its format and file versions, and its device and
number, which must match its name. A device that cannot read a newer
version stops syncing and says why, instead of merging what it cannot
see. An object that fails its seal or its checks is skipped for the same
device's next older one, and the user told. A device remembers the newest
object it read from each other one, so an older object offered again (a
target rolled back) is not read, and the user is told; a target can
still withhold a device's newer objects, or all of them, which is told
too but not prevented.

### What syncs

Hosts, groups and snippets, in the first slice. Not the command history,
recordings, or AI settings. Vault identities come next, each with a flag
that keeps it off the target, default off; the flag sits on the
identity, which hosts only reference.

### Backends

A folder, and git through the `git` command, which uses the user's own
SSH setup, come first; S3 follows, below. Git keeps the objects on a branch of
their own, `tauminus-sync`, in a clone of its own, with commits by
`Tauminus <sync@tauminus.invalid>` at a fixed date, no prompts, and the
transports other than https and ssh off, every object checked. A remote
on disk (a path, `file://`, a Windows share) is refused: pushing to one
runs that repository's own hooks, so a shared folder is the folder
target's. The remote's address, which may hold a token, is passed in
git's environment, never on a command line, and git runs in the clone
whatever `GIT_DIR` and its kin say.
Nothing the remote holds runs, rewrites or hides a file: no hooks, links,
filters, line-ending conversion, fsmonitor, submodules or ignore lists,
and a tree that lacks an object this device wrote is not pushed. A
fetched branch is checked before checkout: only the key and objects, each
a plain file within its size, at most 4096 files and 1 GiB, so a remote
cannot make one stored blob fill the disk on checkout. The fetch itself is
unbounded, as git's is; a tip refused once is not fetched again. Each
publish adds one commit on the branch's tip, so a push sends this
device's object only, and every eighth starts the branch over with one
commit with no parent: an honest remote holds at most eight states,
which anyone who can read the repository can fetch (sealed, with their
order, sizes and which device changed), and what an older one held goes
at the remote's gc. A fetch takes the tip only. The
clone prunes what it no longer needs. Each publish costs the remote about
0.7 MB at 10 000 hosts until its gc. A push that lost a
race fetches, applies this device's changes again (each device touches
only its own files), and goes again. Object names, sizes, counts and times are what a
target sees.

An S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO) is
reached by path-style requests signed with AWS Signature Version 4 in the
`Authorization` header, the payload's SHA-256 signed too. The signer is
ours, about 200 lines on the `hmac` and `sha2` already in the tree and
tested against AWS's published examples; `rusty-s3` was weighed and not
taken, as it signs presigned URLs only, which carry the credential in
the address and leave the payload unsigned, and `aws-sdk-s3` brings
`aws-lc` and some hundred crates. The service is `https`, or `http` to
this machine only; requests take no proxy and follow no redirect. Bucket,
folder and region names are checked to a set that encodes one way. A new
object is sent with `If-None-Match: *`; a service that refuses the header
(B2 does) gets a `HEAD` first, which is enough since each device writes
only its own names. Listing reads only under `devices/` and `key`, so other
data in the bucket costs nothing, at most 64 pages of 8 MiB and 100 000
names, keeping only names a sync object may have; an object larger than
the read limit is refused by its declared length before it is read. Sending
an object may take 60 s plus its size at 128 kbit/s, and reading one
stops after 60 s without a byte, so a large object on a slow link still
arrives and a stalled service does not hold a sync. A refused key (401,
403) is a failure of the target, not of the object. The key id and secret are in the vault record with the sync
key, and the view sees the bucket and the service only.

The pieces sit in the layers they belong to: `Inventory::repaired` in
the domain; the `SyncRemote` port and the `Syncer` use case (merge, save
unless an edit came in meanwhile, publish; no lock held over the
network) in the app; stamping, merging, sealing and the backends in
`tauminus-sync`, which reads and writes the lists through the files' own
JSON (`tauminus_store::interchange`), so a merged list is checked as a
saved one is.

### Trust between devices

Every device with the passphrase writes what the others run: a jump
host, a `ProxyCommand`, a startup snippet. Devices share one key, so a
device can write objects under another's name; the target sees sizes,
counts and times, and deflate lets sizes vary with content.

A host another device changed is not used until the user has seen it.
Each sync, before it saves the merge, notes every host whose exposure
the merge changes, with the SHA-256 fingerprint of what this device had
approved (none for a host new from sync), and writes the note durably
(`sync-review.json`, not synced). The exposure is everything a connect
to the host acts on, listed by `Inventory::exposure`: its address,
protocol, forwards, startup snippet ids, every setting set on it or a
group above it (destructured in full, so a setting added later is
covered without anyone deciding it should be), the `prod` tag, which
turns the guard on, and the text its startup snippets type. Labels,
names and other tags are left out. Every use of a saved
host (an SSH, Mosh or tmux login, SFTP, a forward, a key install,
Telnet, the startup text, a rule that starts with its host) reads the
host and then checks: a value read after a sync saved it was noted
first, so the check sees it. The check never clears a note. A session
already open on a host waiting for review keeps the safe values: its
prod guard on without the allow patterns, the default highlight sets
only, no history, and no output for the AI assistant. The user accepts
hosts as shown, by their fingerprints, a page of 20 at a time; the note
then holds what was shown, so a sync saving other values meanwhile
leaves them held, and a note whose host is as approved goes at the next
sync that leaves it so. A local edit moves the notes it touches along
with it when they held the host as it was just before, read under the
edited book's lock: the user's own edit is no change to review. A sync
saves the snippets only while the hosts still hold its merge, under the
hosts' lock: a host edited between the two saves to list a snippet the
merge changed is merged, and noted, again.
The notes are read from disk at each use, so a second window of the app
sees what the first noted, and a save another window beat is tried
again on what it wrote, against the version that change read; what was
parsed is kept while the file's bytes hash the same, 0.3 ms a read at
10 000 notes. A note that cannot be saved stops the sync
before anything is saved; a review list that cannot be read stops every
use of a saved host. A noted host is hashed only when a merge touches
it, its groups or its startup snippets. Holding the change back in the merge was
weighed and not taken: the CRDT would publish a value this device does
not hold, or diverge.

### In the app

The vault keeps the target and the sync key as one record: a remote's
address may hold a token, so nothing about sync is written outside the
vault but the engine's state and the git clone (`sync/`). Sync needs the
vault open; reading the record is no use of it, so a sync in the
background never keeps the vault from locking. Starting or joining wipes
`sync/` first: an earlier target's device id and numbering would not fit.
Stopping forgets the record, then wipes `sync/`; the target and the
other devices keep everything.

Sync runs on unlock, every 5 minutes while the vault is open, 30 s after
the lists last changed, and on demand; one at a time, and the schedule
skips a run while one goes. An edit saved in the instant after a run
waits for the next tick. The target last opened is kept between runs,
so a git remote remembers the tip it refused, and dropped when the vault
locks, with any token in its address.

## Consequences

- Two devices editing different fields of a host offline keep both; the
  same field keeps the edit synced later, and both devices list the
  other.
- A sync that merges costs O(H + G): about 2 s and 300 MB at 10 000
  hosts of ten fields; hosts at their list limits cost more, in
  proportion to `hosts.json`. One with nothing new costs a hash of the
  lists and a listing of the target, about 0.3 s.
- Taking a credential off the target removes it from each device's next
  object, within the hour; a git remote keeps the replaced ciphertext for
  up to eight publishes and then until its gc, and a folder sync tool may
  keep old versions of its own.
- A device joining a sync reviews each host once before using it, and
  any device reviews a host again after another changes any setting of
  it or its groups, harmless ones included. Noting a merge costs
  O(H·(d + k)) comparisons for depth d and k startup snippets, and
  hashing only the hosts the merge touched; a check reads the review
  list and, for a noted host, hashes it in place, O(d + s) for startup
  text s.
- A snippet another device edited and run by hand from the palette is
  not reviewed; only startup snippets are.
- A use that reads a host, then checks it, passes if two syncs between
  the two changed the host and changed it back: the check hashes the
  host as it is then. Each sync takes seconds over the network; the
  window is the microseconds between read and check.
- The fingerprint an accept sends is a hash of what `hosts_list` and
  `snippets_list` already show, so a webview running an attacker's
  script could accept hosts the user never saw, or save a held host back
  to what was approved and then to the synced values, which a local
  edit takes as the user's. Such a script already
  types into every shell; binding accepts to a token from the review
  would close it.
- Two app processes on one config folder compare and rename the review
  list without a lock between them, and each merges against its own
  copy of the hosts: a save in the microseconds between another's read
  and rename is lost, and one process syncing an old copy can drop a
  note the other just made. One window per user is the common case; a
  single-instance lock would close both.
